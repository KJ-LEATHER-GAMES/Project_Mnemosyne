# ATS有料まとめ記事 企画書（改訂版）

## 1. 企画の目的

本企画書は、ATS（Adventure Token System）に関する開発日記・技術記事を、将来的に1本の有料まとめ記事へ育てるための設計文書である。

本企画書で扱う対象は、単なる記事目次ではない。読者、提供価値、無料記事との接続、記事スコープ、特典・副産物、価格方針、更新方針までを整理し、ATS有料まとめ記事を「読者が実践に使える資産記事」として設計することを目的とする。

現時点では、以下を主な目的とする。

- ATS有料まとめ記事のコンセプトを明確にする
- 想定読者と読者のBefore / Afterを定義する
- 記事で提供する価値を整理する
- 既存の開発日記・技術記事との接続方針を決める
- 初版で扱う範囲と、将来追記に回す範囲を切り分ける
- 今後の無料記事投稿を、有料記事の素材・導線・信頼形成に接続する

本記事は、ひらかわ式の「1記事を育てる」考え方を参考にする。ただし、最初から高額一本勝負を狙うのではなく、まずは無料記事群で信頼と素材を蓄積し、その後に1本の有料まとめ記事へ統合する方針とする。

本企画書における判断基準は以下とする。

| 判断軸 | 採用するもの | 採用しないもの |
|---|---|---|
| 読者価値 | 読者が自分の課題に応用できるもの | こうちゃんの作業ログで終わるもの |
| 技術範囲 | 要件・設計・実装がつながるもの | 技術の網羅解説 |
| 家庭文脈 | 判断背景として必要なもの | 個人情報や家庭事情に踏み込みすぎるもの |
| コード | 設計理解を助けるもの | コピペ完成品として誤解されるもの |
| 特典 | 実践を助けるもの | 作る負荷が高すぎるもの |
| 有料化 | 体系化・再利用性があるもの | 無料記事の焼き直し |

本企画書は、今後の執筆・素材整理・特典設計の基準として運用する。

## 2. 記事コンセプト

本記事のコンセプトは、**家庭内ポイント制度を題材に、現実のあいまいな課題を要件定義し、LINE Botとして実装・運用するまでの実践ガイド**である。

ATS（Adventure Token System）は、単なる子ども向けポイント制度でも、単なるLINE Bot開発チュートリアルでもない。

出発点は、家庭内のリアルな課題である。

子どもの行動を「やった／やらない」で責めるのではなく、行動を加点で支援したい。親が毎回記録・集計する運用は続かないため、入力や管理の負担を減らしたい。行動の蓄積を見える化し、本人にも親にも「進んでいる感」が残るようにしたい。

このようなあいまいな家庭内運用を、行動マスタ、ポイント、制限ルール、履歴、残高、ごほうび交換といった仕様に分解し、最終的にLINE Botとして実装・運用するまでの過程を整理する。

本記事で扱う中心テーマは、コードそのものではなく、**現実の課題をどう仕様に変換し、どう実装可能な形に落とし込むか**である。

そのため、本記事では以下の観点を一体で扱う。

- 家庭内ポイント制度の設計思想
- 紙運用からシステム化するまでの判断
- 行動マスタ、ポイント、制限ルール、ごほうびの設計
- LINE Botのpostback設計
- UseCase、Repository、DB設計
- cooldown、daily_limit、冪等性などの運用上の制約
- 実際に運用して見えてきた改善点
- 読者が自分の家庭や個人開発に応用できるテンプレート

既存の開発日記や技術記事は、個別テーマごとの気づきや判断を扱う。一方で、本記事はそれらを統合し、要件定義から設計、実装、運用改善までを順番にたどれる体系化されたまとめ記事とする。

読者に届けたい価値は、単に「LINE Botが作れるようになること」ではない。

小さな家庭内アプリであっても、現実の課題を丁寧に分解すれば、要件定義・DB設計・ユースケース設計・運用改善まで含んだ実践的な個人開発になる。本記事では、その過程をATSの実例を通じて具体的に示す。

また、本記事はATSをそのまま再現するためだけの記事ではない。読者が自分の家庭・仕事・個人開発の課題を仕様化するための参照事例として使える記事にする。

したがって、本記事の仮タイトルは以下とする。

> **家庭内ポイント制度を題材に学ぶ、要件定義からLINE Bot実装までの個人開発実践ガイド**

## 3. 想定読者

本記事の主な想定読者は、**家庭内ポイント制度という身近な題材を通じて、現実の課題を要件定義・設計・LINE Bot実装に落とし込む流れを学びたい個人開発者**である。

ただし、記事の入口は技術だけに限定しない。

ATSの出発点は、家庭内のリアルな課題である。子どもの行動を責めずに支援したい。親の記録・集計負担を減らしたい。紙のポイント制度では曖昧に流せることも、システム化すると仕様として決める必要が出てくる。

この家庭内の悩みを入口にしながら、記事の中心価値は、あいまいな課題を要件定義し、行動マスタ、ポイント、制限ルール、履歴、残高、ごほうび、LINE Bot、DB設計に落とし込む過程に置く。

想定読者は、大きく3層に分ける。

### 3.1 本命読者：個人開発者・エンジニア寄り読者

本記事の本命読者は、個人開発やWebアプリ開発に関心があり、実例を通じて設計と実装の流れを学びたい人である。

より具体的には、**TypeScriptやWeb APIの基礎は理解しているが、個人開発で要件定義・DB設計・UseCase設計まで一気通貫で進める経験はまだ少ない人**を想定する。

具体的には、以下のような人である。

- TypeScriptやWeb APIの基礎は理解している
- LINE BotやWebhookに興味がある
- 個人開発をしてみたいが、題材選びや設計で止まっている
- 作りたいものはあるが、要件定義やDB設計に自信がない
- Controller / UseCase / Service / Repository の責務分担を実例で学びたい
- 仕様書、DB設計、postback.data設計、UseCase設計を一連の流れで見たい
- コードだけでなく、なぜその設計にしたのかという判断過程を知りたい

この読者に対して、本記事は「家庭内ポイント制度」という具体的な題材を使い、要件定義からLINE Bot実装、運用改善までを一気通貫で学べる実践ガイドとして機能する。

### 3.2 入口読者：子育て・家庭内ポイント制度に関心がある親

本記事は、技術者だけに閉じた内容にはしない。

ATSの入口には、子育てや家庭内運用の悩みがある。

具体的には、以下のような読者にも届く内容とする。

- 子どもに「やりなさい」と言い続けることに疲れている
- 行動を責めるのではなく、できたことを加点で支援したい
- 家庭内ポイント制度やスタンプカードに興味がある
- 紙のポイント表を試したが、記録や集計が続かなかった
- ごほうび設計やポイントバランスに悩んでいる
- 子どもの行動を見える化したい
- まずは家庭内ルールの作り方だけでも知りたい

この層は、必ずしも自分でLINE Botを実装するとは限らない。しかし、家庭内ポイント制度の考え方、紙運用から始める判断、ポイントやごほうびの設計には強く関心を持つ可能性がある。

そのため、無料部分や前半の章では、家庭内の悩みや運用判断を丁寧に扱う。一方で、有料部分の中心価値は、設計・実装・運用改善まで踏み込んだ実践内容に置く。

### 3.3 周辺読者：要件定義・業務改善・仕組み化に関心がある人

本記事は、家庭内ポイント制度という題材を扱うが、学べる内容は家庭内に限定されない。

現実のあいまいな課題を、ルール・データ・画面・処理・制限に分解していく過程は、業務改善や要件定義にも応用できる。

そのため、以下のような読者も対象に含める。

- 要件定義を身近な題材で学びたい人
- 業務改善や運用設計に関心がある人
- 紙運用をシステム化するときの考え方を知りたい人
- ルール設計、制限設計、例外処理に興味がある人
- 個人開発を通じて設計力を高めたい人

この読者にとって、ATSは「家庭内の小さなアプリ」ではなく、現実の運用を仕様に変換する実例となる。

### 3.4 主対象にしない読者

本記事は、すべての読者を対象にはしない。

特に、以下のような読者は主対象にしない。

- コードや設計の話を一切読みたくない人
- 子育てノウハウだけを求めている人
- 完成済みアプリだけがほしい人
- LINE Botの最短実装手順だけを知りたい人
- コピペだけで動くコード集を期待している人
- 育児の正解や家庭運用の万能解を求めている人

本記事で提供するのは、完成済みの答えではなく、家庭内のリアルな課題を仕様化し、実装し、運用しながら改善していく過程である。

### 3.5 読者への約束

本記事で読者に約束することは、次の通りである。

> 家庭内ポイント制度という身近な題材を通じて、あいまいな課題を要件定義し、行動・ポイント・制限・履歴・ごほうび・LINE Bot・DB設計に落とし込む流れを、実例ベースで学べるようにする。

一方で、以下のことは約束しない。

- これを読めば誰でも子どもの行動が必ず変わる
- この通りにすればすべての家庭の問題が解決する
- コピペだけで完璧なLINE Botが完成する
- すべての家庭にそのまま適用できる
- 育児の正解を提示する

本記事の価値は、答えを押し付けることではなく、読者が自分の家庭や自分の個人開発に応用できる考え方・設計手順・実例を提供することにある。

## 4. 読者のBefore / After

本記事では、読者に対して単なる知識提供ではなく、**現実のあいまいな課題を、要件定義・設計・実装・運用改善に落とし込めるようになる変化**を提供する。

ATS（Adventure Token System）は、家庭内ポイント制度という身近な題材を扱う。しかし、本記事で届けたい価値は「家庭内ポイント制度の紹介」にとどまらない。

子どもの行動支援、紙運用、ポイント設計、ごほうび設計、LINE Bot、DB設計、制限判定、冪等性、運用改善までを一連の流れとして扱うことで、読者が自分の家庭・個人開発・業務改善にも応用できる設計プロセスを学べる状態を目指す。

### 4.1 本命読者のBefore / After

本記事の本命読者は、個人開発・要件定義・LINE Bot設計に関心があるエンジニア寄り読者である。

この読者は、コードを書くこと自体には興味がある。一方で、実際の個人開発では、何を作るか、どう要件に分解するか、どのようにDBやUseCaseへ落とすかで詰まりやすい。

本記事では、家庭内ポイント制度という具体的な題材を通じて、その詰まりを解消する。

| Before | After |
|---|---|
| 個人開発をしたいが、題材選びで止まっている | 身近な課題を個人開発の題材に変換できる |
| 作りたいものはあるが、要件定義の進め方が分からない | 現実の悩みを、行動・ルール・制限・データに分解できる |
| LINE Botを作ってみたいが、全体設計が見えない | postback.data、Webhook、UseCase、DB更新までの流れを理解できる |
| DB設計が場当たり的になりやすい | 履歴、残高、集計、冪等性、同期キューを分けて設計できる |
| Controller / Service / Repository の責務分担が曖昧 | UseCaseを中心に、処理の責務を整理できる |
| 技術記事を読んでも実運用のイメージが湧かない | 実際に家庭で使うシステムの運用改善までイメージできる |
| コードだけを真似して終わってしまう | なぜその設計にしたのかという判断過程まで理解できる |
| 個人開発が場当たり的に進みやすい | 要件定義、設計、実装、確認、改善の流れで進められる |

この読者に対して、本記事が提供する変化は以下である。

> 小さな家庭内アプリを題材に、現実の課題を要件定義し、設計書・DB・UseCase・LINE Bot実装・運用改善まで落とし込めるようになること。

つまり、本記事は単なるLINE Bot開発記事ではなく、個人開発における「設計の型」を学ぶための記事である。

### 4.2 入口読者のBefore / After

本記事の入口読者は、子育て・家庭内ポイント制度に関心がある親である。

この読者は、必ずしも自分でアプリを作りたいわけではない。しかし、子どもの行動を責めずに支援したい、親の記録負担を減らしたい、家庭内ポイント制度をうまく設計したいという悩みを持っている。

ATSの出発点は、まさにこの家庭内の悩みである。

| Before | After |
|---|---|
| 子どもに「やりなさい」と言い続けることに疲れている | 行動を責めず、できたことを加点する考え方を持てる |
| 家庭内ポイント制度を作りたいが、何から決めればよいか分からない | 行動、ポイント、制限、ごほうびの順に整理できる |
| 紙のポイント表やスタンプカードが続かない | まず紙で試し、必要に応じて仕組み化する判断ができる |
| ポイントを付けすぎてインフレしそうで不安 | ポイントバランス、日次上限、ごほうび価格を考えられる |
| ごほうびの設定に迷う | 小・中・大の報酬設計を考えられる |
| 親の記録・集計負担が大きい | どこを手作業にし、どこを自動化すべきか見えてくる |
| 子どもの行動の蓄積が見えない | 行動履歴やポイント残高として可視化する発想を持てる |

この読者に対して、本記事が提供する変化は以下である。

> 子どもの行動を責めるのではなく、行動を記録し、加点し、見える化する家庭内ポイント制度の設計方法を理解できるようになること。

ただし、本記事は育児の正解を提示するものではない。家庭によって合う運用は異なるため、ATSはあくまで一つの実例として扱う。

本記事では、家庭内ポイント制度をそのまま真似してもらうことよりも、読者が自分の家庭に合わせてルールを調整できるようになることを重視する。

この読者に対して、本記事が提供する変化は以下である。

> 家庭内の小さな仕組み化を題材に、現実の運用を仕様・データ・処理・制限・改善に分解する考え方を学べるようになること。

### 4.4 本記事全体で提供する変化

本記事全体で提供するBefore / Afterは、以下の一文に集約できる。

**Before：**  
身近な課題や家庭内ルールをアプリ化したいと思っても、何を要件として定義し、どのように設計・実装・運用改善へ落とし込めばよいか分からない。

読者に届けたい本質的な変化は、次の通りである。

> 現実の課題を仕様に変え、仕様を設計に変え、設計を動く仕組みに変え、運用しながら改善できるようになること。

### 4.5 Before / Afterから見た記事の価値

| 信頼価値 | 実際の家庭運用に基づく一次情報 |

この分類により、本文で伝える価値と、特典・副産物として提供する価値を分けて設計する。

### 5.3 課題整理の価値

ATSの出発点は、家庭内のリアルな悩みである。

子どもの行動を責めずに促したい。親の記録・集計負担を減らしたい。行動の蓄積を見える化したい。ごほうびを使いながら、無理なく継続できる仕組みにしたい。

これらは、最初から明確な仕様として存在していたわけではない。

本記事では、こうしたあいまいな悩みを、以下のように要件へ変換していく過程を示す。

- 何を行動として記録するのか
- どの行動に何ポイント付けるのか
- 1日に何回まで認めるのか
- 連打や重複をどう防ぐのか
- ポイントを貯めるだけでなく、どう使うのか
- 親の手間をどこまで減らすのか
- 紙運用で十分な部分と、システム化すべき部分をどう分けるのか

この過程を通じて、読者は「現実の悩みを仕様にする」考え方を学べる。

### 5.4 ルール設計の価値

家庭内ポイント制度は、一見すると単純に見える。

しかし、実際に運用しようとすると、以下のような設計判断が必要になる。

- ポイントは通貨なのか、経験値なのか
- レベルは報酬倍率なのか、解放条件なのか
- アイテムは常時効果なのか、一時効果なのか
- ごほうびはポイント消費型にするのか、累計到達型にするのか
- 同じ行動を何回まで許可するのか
- 何分空ければ再報告できるのか
- 日次上限を設けるべきか
- 子どもが萎えないポイント設計にするにはどうするか

本記事では、こうした判断を、ATSの実例を通じて整理する。

特に、以下の設計は重要な提供価値になる。

- 行動マスタ設計
- ポイントバランス設計
- cooldown設計
- daily_limit設計
- 日次ポイント上限設計
- 所持ポイントと累計ポイントの分離
- ごほうび交換ルール
- スタンプ・抽選・ボーナスの段階導入

読者は、単なる「ポイント制度の例」ではなく、家庭内ルールをシステムで扱えるレベルまで具体化する方法を学べる。

### 5.5 技術設計の価値

本記事の本命読者にとって、重要な価値は技術設計である。

ATSでは、家庭内ポイント制度をLINE Botとして実装する。そのために、以下の要素を一連の流れとして扱う。

- LINEのリッチメニュー

- 制限判定
- ポイント計算
- DB更新
- LINE返信
- Notion同期
- 手動確認
- 運用改善

本記事では、これらを個別の技術要素としてではなく、1つのユースケースとしてつなげて説明する。

特に、以下の技術設計は読者にとって再利用価値が高い。

- postback.dataの設計方法

### 5.6 実装理解の価値

本記事では、設計だけでなく、実装に落とし込む過程も扱う。

ただし、価値の中心は「コピペで動くコード集」ではない。

価値の中心は、**仕様がどのようにコードへ変換されるのかを理解できること**である。

たとえば、以下のような流れを扱う。

- activity_logsに履歴を保存する

この流れを通じて、読者は要件・設計・DB・コードがどのようにつながるかを理解できる。

### 5.7 運用改善の価値

- スタンプや抽選はいつ導入すべきか
- 所持ポイントと累計ポイントを分けるべきか

本記事では、こうした運用後の見直しも価値として扱う。

特に、個人開発では「リリース後の改善」まで語られる記事は多くない。ATSでは、家庭内で実際に使うからこそ、仕様変更や改善判断が発生する。

| 出さない情報 | 個人が特定される情報、本人の尊厳を損なう内容、将来不利益になり得る詳細 |

記事内では、子どもの話を「設計判断の背景」として扱う。読者の興味を引くために家庭事情を消費する書き方は避ける。

また、以下の表現方針を守る。

- 子どもを評価対象として書かない
- 「できないこと」より「仕組みで支援したいこと」を中心に書く
- 家庭内の具体事情は、必要に応じて一般化する
- 親としての迷いは書いても、子ども本人の内面を断定しない

### 6.8 テンプレート・特典の初版範囲

この方針により、初版特典を増やしすぎず、有料記事としての実用価値と公開しやすさのバランスを取る。

## 7. 既存連載との接続

本記事は、ATSに関する開発日記・技術記事を単純に再編集した総集編ではない。

既存記事は、それぞれ単発で読める無料記事として公開しながら、将来的には有料まとめ記事の信頼形成・導線・素材として活用する。

無料記事群の役割は、読者に以下を伝えることである。

- ATSが実際の家庭内課題から始まっていること
- 紙運用からLINE Bot化まで、段階的に考えていること
- ポイント、レベル、アイテム、ごほうびなどを感覚ではなく設計対象として扱っていること
- TypeScript、LINE Bot、DB設計、UseCase設計などを実際に組み合わせていること
- 机上のチュートリアルではなく、実運用しながら改善していること

一方、有料まとめ記事の役割は、これらの個別記事を体系化し、読者が要件定義から設計・実装・運用改善までを順番にたどれる形に再構成することである。

### 7.1 既存記事の基本的な役割

ATS関連の記事は、大きく以下の3種類に分ける。

| 記事タイプ | 役割 | 有料記事との接続 |
|---|---|---|
| 開発日記 | 家庭内の悩み、判断の変化、試行錯誤を伝える | 有料記事の背景・事例・判断理由になる |
| 技術記事 | 設計・実装・DB・UseCaseなどの技術的な学びを伝える | 有料記事の技術章・設計章の素材になる |
| まとめ・振り返り記事 | 複数テーマを整理し、読者の理解を助ける | 有料記事への導線・入口になる |

開発日記は、読者に共感と物語性を届ける。技術記事は、読者に設計力・実装力・再現性を示す。有料まとめ記事は、それらを統合し、読者が自分の課題に応用できる実践ガイドとして提供する。

### 7.2 投稿済み・準備中・今後書く記事の整理

既存記事との接続を考えるときは、投稿済み記事、下書き・準備中記事、今後書くべき記事、有料記事で新規に書く内容を分けて管理する。

| 区分 | 内容 | 役割 |
|---|---|---|
| 投稿済み記事 | すでに公開され、有料記事に接続できる記事 | 信頼形成・初期導線 |
| 下書き・準備中記事 | 企画や素材はあるが、公開前の記事 | 有料記事の素材蓄積 |
| 今後書くべき記事 | 有料記事に必要だが、まだ素材が足りない記事 | 無料導線の強化 |
| 有料記事で新規に書く内容 | 無料記事では出さず、有料側で体系化する内容 | 商品価値の中核 |

この整理により、無料記事で出すべき内容と、有料記事で体系化する内容を分けられる。

### 7.3 開発日記との接続

開発日記は、ATSの「なぜ」を伝える記事群である。

家庭内ポイント制度を作ろうとした背景、紙運用から始めた理由、ポイント・レベル・アイテムを分けた判断、ポイントバランスの調整、ごほうび設計などは、技術だけでは伝わりにくい。

開発日記では、以下のような要素を蓄積する。

- 家庭内で実際に起きた困りごと
- 最初に考えた案
- うまくいかなかった案
- 採用した方針
- 採用しなかった理由
- 運用して見えてきた違和感
- 親としての判断
- 開発者としての判断

これらは、有料まとめ記事では「設計判断の背景」として再利用する。

| 開発日記テーマ | 有料記事での使い方 |
|---|---|
| 小3の娘向けに家庭内ポイント制度を作ろうとした話 | 企画背景・課題定義の章に接続する |
| 紙のぼうけんカードから始めた理由 | 紙運用とシステム化の境界を説明する章に接続する |
| ポイント・レベル・アイテムを分けた話 | ドメイン設計・ルール設計の章に接続する |
| ポイントバランス調整の話 | ポイント設計・インフレ防止の章に接続する |
| 紙運用からLINE Botへ移行した話 | MVP設計・段階導入の章に接続する |
| ごほうび設計の見直し | 報酬設計・所持ポイントと累計ポイントの章に接続する |
| 運用後に見えた改善点 | 運用改善・Ver.1.1検討の章に接続する |

開発日記は、有料記事の本文にそのまま貼り付けるのではなく、判断プロセスを抽出して再構成する。

無料記事では「そのとき何を考えたか」を伝え、有料記事では「読者が自分で判断するための設計観点」として整理する。

### 7.4 技術記事との接続

技術記事は、ATSの「どう作るか」を伝える記事群である。

LINE BotのWebhook処理、postback.data設計、DFD、DTO契約図、DB設計、UseCase設計、Repository責務、冪等性、制限判定などは、有料まとめ記事の技術的な中核になる。

技術記事では、以下のような要素を蓄積する。

- 実装前に描いた設計図
- postback.dataの契約
- WebhookからUseCaseまでの流れ
- DTOや型定義の考え方
- DBテーブルの責務
- トランザクション境界
- cooldown / daily_limit / 冪等性の判定
- 手動確認手順
- 実装中に発生したエラーと修正判断

これらは、有料まとめ記事では「実装手順」ではなく、「仕様がどう設計とコードに変換されるか」を説明する材料として使う。

| 技術記事テーマ | 有料記事での使い方 |
|---|---|
| LINE BotのWebhook処理 | LINE Bot全体構成・イベント処理の章に接続する |
| postback.data設計 | UI操作とUseCase契約の章に接続する |
| DFDとDTO契約図 | 要件から実装へ落とす設計手法の章に接続する |
| ユーザー操作一覧からAPI設計へ落とす話 | 画面・操作・API・DBの接続章に使う |
| DB設計 | 正本DB、履歴、残高、集計、冪等性の章に接続する |
| UseCase / Service / Repository責務 | アーキテクチャ設計の章に接続する |
| cooldown / daily_limit確認 | 制限ルールを実装する章に接続する |
| 重複防止・冪等性確認 | 実運用で壊れない設計の章に接続する |
| ごほうび申請・承認設計 | 報酬交換フローの章に接続する |

技術記事は、有料記事における信頼材料でもある。

無料記事で技術的な考え方や実装判断を見せておくことで、有料まとめ記事に対して「この人は実際に設計して実装している」という信頼が生まれる。

### 7.5 無料記事と有料記事の役割分担

無料記事と有料記事は、同じ内容を単純に無料・有料で分けるのではない。

無料記事では、個別テーマごとの気づき・判断・学びを出す。有料記事では、それらを順番に並べ替え、読者が自分で再現・応用できる形に体系化する。

| 区分 | 無料記事 | 有料まとめ記事 |
|---|---|---|
| 目的 | 読者との接点を作る | 読者が実践できるようにする |
| 内容 | 個別テーマの気づき・判断・実装メモ | 要件定義から運用改善までの体系化 |
| 読み方 | 単発で読める | 順番に読み進める |
| 価値 | 共感、学び、信頼形成 | 実践手順、テンプレート、設計書、再利用性 |
| 役割 | 導線・素材・信頼形成 | 商品本体 |
| 更新 | 継続的に投稿 | 素材がたまった段階で統合・追記 |

この役割分担により、無料記事を読んだ人が、有料まとめ記事に対して以下のように感じる状態を目指す。

- 個別記事は読んできたが、全体像を通して理解したい
- 自分でも同じような仕組みを作ってみたい
- 設計書やテンプレートとして再利用したい
- 判断の背景だけでなく、実装までの全体フローを知りたい
- バラバラの記事ではなく、体系化された形で読みたい

### 7.6 有料記事への導線として残す無料記事

既存記事の一部は、有料まとめ記事の導線として特に重要になる。

導線記事として機能しやすいのは、以下のような記事である。

| 導線タイプ | 記事テーマ例 | 読者に与える印象 |
|---|---|---|
| 共感導線 | 家庭内ポイント制度を作ろうとした話 | 自分の家庭にも近い悩みがある |
| 判断導線 | 紙運用からLINE Botへ移行した話 | いきなり作らず段階導入している |
| 設計導線 | ポイント・レベル・アイテムを分けた話 | 感覚ではなく設計している |
| 技術導線 | postback.dataやWebhook設計の話 | 実装まで踏み込んでいる |
| 信頼導線 | DFDとDTO契約図の記事 | 設計できる人だと伝わる |
| 運用導線 | cooldown / daily_limit / 冪等性の確認記事 | 実運用で壊れない仕組みを考えている |

これらの記事の末尾には、将来的に有料まとめ記事への導線を設置する。

導線文は、単なる販売告知ではなく、以下のような位置づけにする。

> この記事では個別テーマとして扱いましたが、ATS全体の要件定義・設計・実装・運用改善の流れは、有料まとめ記事で体系化しています。

このように、無料記事を読んだ人が自然に次へ進める導線を作る。

### 7.7 有料記事で再構成する観点

有料まとめ記事では、既存記事を時系列順に並べるだけでは不十分である。

読者が実践しやすいように、以下の順番で再構成する。

1. なぜ作るのか
2. 何を解決するのか
3. どこまでをMVPにするのか
4. 家庭内ルールをどう仕様化するのか
5. 行動・ポイント・制限・ごほうびをどう設計するのか
6. LINE BotのUIとpostback.dataをどう設計するのか
7. DBとUseCaseをどう設計するのか
8. 実装時にどこで詰まり、どう直したのか
9. 実際に運用して何を見直したのか
10. 読者が自分の課題に応用するにはどうすればよいか

この順番に再構成することで、既存記事の単なる再録ではなく、読者が実践できる有料記事になる。

### 7.8 既存記事を今後どう書くか

今後の開発日記・技術記事は、有料まとめ記事の素材になる前提で書く。

そのため、各記事には以下の要素を意識的に残す。

- 何に困ったのか
- 最初にどう考えたのか
- どんな選択肢があったのか
- 何を採用したのか
- 何を採用しなかったのか
- 判断理由は何か
- 実装や運用で何が起きたのか
- 次に見直すべきことは何か
- 有料まとめ記事に転用できる図解・テンプレート・コードは何か

特に重要なのは、「結論」だけでなく「判断過程」を残すことである。

有料まとめ記事の価値は、完成形だけではなく、どのように考えてその形に至ったかにある。

### 7.9 既存記事との接続方針まとめ

既存記事との接続方針は、以下の通りである。

1. 開発日記は、家庭内の悩み・判断・試行錯誤を蓄積する
2. 技術記事は、設計・実装・確認手順を蓄積する
3. 無料記事は、読者との接点・信頼形成・有料記事への導線として機能させる
4. 有料まとめ記事では、既存記事を再録せず、実践できる順番に再構成する
5. 各記事の末尾には、将来的に有料まとめ記事への自然な導線を設置する
6. 今後の記事は、有料記事の素材になる前提で、判断過程・図解・テンプレート化候補を残す

この方針により、ATSの無料連載は、単なる投稿履歴ではなく、有料まとめ記事を育てるための素材群として機能する。

## 8. 無料部分の設計方針

本章では、ATS有料まとめ記事における無料部分の役割と設計方針を定義する。

本記事の無料部分は、単なる冒頭の試し読みではない。読者が「この記事は自分に関係がある」「有料部分を読む価値がある」「購入後に何が得られるか分かる」と判断するための導入部分である。

特に本記事は、家庭内ポイント制度、子育て、要件定義、LINE Bot、DB設計、個人開発という複数の文脈をまたぐ。そのため、無料部分では読者の入口を広く取りつつ、有料部分で扱う中心価値を明確に伝える必要がある。

無料部分の目的は、以下である。

* 読者の悩みを言語化する
* ATSがどのような課題から始まったのかを伝える
* 本記事が単なる子育て記事でも、単なるLINE Bot実装記事でもないことを伝える
* 有料部分で得られる内容を明確にする
* 購入前の不安を減らす
* 既存無料記事から有料記事へ自然に接続する

無料部分では、読者に十分な納得感を与える。一方で、有料部分の中核となる具体的な設計手順、テンプレート、実装判断、DB設計、UseCase設計の詳細は、有料部分に残す。

---

### 8.1 無料部分の役割

無料部分の主な役割は、読者に対して「この記事を読む理由」と「有料部分に進む理由」を明確にすることである。

本記事の入口は、家庭内ポイント制度という身近なテーマに置く。

子どもの行動を責めるのではなく、できた行動を加点で支援したい。親が毎回記録・集計する運用は続かない。紙のポイント表では始めやすいが、続けていくとルールや集計が曖昧になる。LINE Bot化すれば便利になりそうだが、実際に作ろうとすると、行動、ポイント、制限、履歴、ごほうび、DB、UseCaseなど、決めるべきことが急に増える。

このような読者の悩みを無料部分で丁寧に扱う。

ただし、無料部分の役割は共感だけではない。

本記事では、家庭内の悩みを出発点にしながら、中心価値は要件定義・設計・実装・運用改善に置く。そのため、無料部分では以下の流れを明確に示す。

1. 家庭内ポイント制度を作ろうとした背景
2. 紙運用から始めた理由
3. システム化すると急に仕様が必要になること
4. LINE Bot化するうえで必要になる設計要素
5. 有料部分で扱う具体的な内容
6. 読者が得られる成果物・テンプレート
7. 本記事が約束すること、約束しないこと

無料部分は、読者に「これは自分のための記事だ」と感じてもらう入口であり、有料部分は「では、実際にどう設計するのか」を体系的に扱う本体である。

したがって、無料部分では以下を重視する。

| 役割       | 内容                                           |
| -------- | -------------------------------------------- |
| 共感形成     | 家庭内ポイント制度、子どもの行動支援、親の記録負担などの悩みを言語化する         |
| 価値提示     | 本記事が、要件定義からLINE Bot実装までの実践ガイドであることを示す        |
| 対象読者の明確化 | 誰に向けた記事で、誰には向かない記事かを明確にする                    |
| 商品説明     | 有料部分で扱う内容、テンプレート、設計書、コードの扱いを示す               |
| 不安解消     | コピペ完成品ではないこと、育児の正解ではないこと、家庭に合わせた応用が必要なことを伝える |
| 導線形成     | 既存の開発日記・技術記事から有料記事へ自然に接続する                   |

無料部分は、有料記事の「前置き」ではなく、購入判断のための設計された導入部として扱う。

### 8.2 無料部分で伝える読者の悩み

無料部分では、読者の悩みを複数の入口から言語化する。

本記事の想定読者は、主に以下の3層である。

* 個人開発・要件定義・LINE Bot設計に興味があるエンジニア寄り読者
* 子育て・家庭内ポイント制度に関心がある親
* 要件定義・業務改善・仕組み化に関心がある人

それぞれの読者が抱える悩みは異なるが、共通しているのは、現実のあいまいな課題を仕組みに落とし込む難しさである。

#### 本命読者の悩み

本命読者である個人開発者・エンジニア寄り読者には、以下の悩みがある。

* 個人開発をしたいが、題材選びで止まっている
* 作りたいものはあるが、要件定義の進め方が分からない
* LINE BotやWebhookに興味はあるが、実際のユースケースに落とせない
* DB設計が場当たり的になりやすい
* Controller、UseCase、Service、Repositoryの責務分担が曖昧になる
* 実装前にどこまで設計すればよいか分からない
* 実運用で必要になる制限や例外処理を後回しにしてしまう
* コード例だけを読んでも、自分の開発に応用できない

この読者に対しては、家庭内ポイント制度という具体的な題材を使い、要件定義、行動マスタ、ポイント設計、制限判定、LINE Bot、DB、UseCaseまでを一連の流れで扱うことを伝える。

#### 入口読者の悩み

入口読者である子育て・家庭内ポイント制度に関心がある親には、以下の悩みがある。

* 子どもに「やりなさい」と言い続けることに疲れている
* できなかったことより、できたことを見える化したい
* 家庭内ポイント制度を作りたいが、何から決めればよいか分からない
* 紙のスタンプカードやポイント表が続かない
* ポイントを付けすぎてインフレしそうで不安
* ごほうびの価格設定に迷う
* 親の記録・集計負担を減らしたい
* 子どもが自分で報告できる仕組みにしたい

この読者に対しては、ATSが家庭内の悩みから始まった実例であり、最初からアプリ化するのではなく、紙運用から段階的に考えていることを伝える。

#### 周辺読者の悩み

周辺読者である要件定義・業務改善・仕組み化に関心がある人には、以下の悩みがある。

* 現実のあいまいな課題をどう仕様にすればよいか分からない
* 紙運用をシステム化するときの考え方を知りたい
* 業務ルールや家庭内ルールをデータ構造に落とす練習をしたい
* 例外処理や制限設計をどの段階で考えるべきか知りたい
* 要件、フロー、DB、UseCase、コードのつながりを実例で見たい

この読者に対しては、ATSを「家庭内の小さなアプリ」ではなく、現実の運用を仕様に変換する実例として位置づける。

無料部分では、これらの悩みを読者が自分ごととして捉えられるように書く。

特に重要なのは、以下の問題提起である。

> 紙や口約束では曖昧に流せる家庭内ルールも、システム化しようとすると、行動の定義、ポイント、上限、重複、履歴、残高、ごほうびまで、すべて仕様として決める必要が出てくる。

この問題提起が、本記事全体の入口になる。

### 8.4 無料部分で約束しないこと

無料部分では、約束しないことも明確にする。

これは、読者の期待値を調整し、購入後のミスマッチを減らすためである。

本記事は、家庭内ポイント制度を題材にするが、育児の正解を提示するものではない。また、LINE Botを扱うが、コピペだけで完成する実装手順書でもない。

無料部分では、以下を明確に伝える。

| 約束しないこと                    | 理由                          |
| -------------------------- | --------------------------- |
| 子どもの行動が必ず変わること             | 家庭や子どもによって前提が異なるため          |
| すべての家庭でそのまま使えること           | 行動内容、報酬、運用ルールは家庭ごとに調整が必要なため |
| 育児の正解を提示すること               | 本記事は育児論ではなく、仕組み化と設計の実例であるため |
| コピペだけで完成するアプリを提供すること       | 本記事の価値は設計意図と判断過程の理解にあるため    |
| LINE Botの最短実装手順だけを提供すること   | 技術要素だけでなく、要件定義と運用設計を扱うため    |
| DDDやクリーンアーキテクチャを網羅的に解説すること | 必要な責務分担は扱うが、理論の網羅は目的ではないため  |
| 本番運用を完全保証すること              | 環境、家庭運用、利用状況によって条件が変わるため    |
| 完成済みアプリを配布すること             | 読者が自分の文脈に合わせて設計する前提であるため    |

特に注意すべきなのは、子育て文脈での表現である。

本記事では、子どもの行動を評価したり、家庭運用の正解を断定したりしない。ATSは、あくまで「行動を責めずに加点で支援したい」という家庭内の課題から生まれた一つの実例として扱う。

また、技術文脈でも過度な期待を持たせない。

コード例や設計図は提供するが、読者の環境でそのまま動くことを保証するものではない。本文では、実装そのものよりも、なぜその設計にしたのか、どのように仕様をコードへ落としたのかを重視する。

無料部分では、以下のような表現で期待値を調整する。

> 本記事は、家庭内ポイント制度の万能解でも、コピペ完成アプリでもありません。ATSという実例を通じて、現実の課題を要件・設計・実装・運用改善に変換する流れを共有する記事です。

この線引きを無料部分で明示することで、読者との認識違いを減らす。

| 記事タイプ  | 無料記事での役割                    | 有料記事への接続           |
| ------ | --------------------------- | ------------------ |
| 開発日記   | 家庭内の悩み、判断の変化、試行錯誤を伝える       | 背景・課題定義・設計判断の材料になる |
| 技術記事   | 実装、設計、DB、UseCase、Webhookを扱う | 技術章・設計章の材料になる      |
| 図解記事   | ポイント制度やシステム構成を視覚化する         | 有料記事の理解補助になる       |
| 振り返り記事 | 運用後の改善や判断を整理する              | 更新・育成方針の材料になる      |

有料記事の無料部分では、これらの記事を以下のように位置づける。

> これまで個別記事として、家庭内ポイント制度の背景、紙運用からLINE Botへの移行、ポイント設計、LINE BotのWebhook処理、DB設計、UseCase設計などを扱ってきました。本記事では、それらを単純に再録するのではなく、要件定義から設計・実装・運用改善まで順番にたどれる形に再構成します。

#### 開発日記からの接続

開発日記から来た読者は、家庭内ポイント制度や子育て文脈に関心を持っている可能性が高い。

そのため、無料部分では以下を伝える。

* 開発日記では、家庭内の悩みや判断過程を個別に書いている
* 有料記事では、それらを要件定義・設計・実装の流れとして再構成する
* 家庭内ポイント制度を作るときに、何をどの順番で決めればよいかを整理する
* 紙運用、ポイント設計、制限設計、ごほうび設計を体系的に扱う

開発日記からの導線文は、以下のようにする。

> 開発日記では、ATSを作る過程で考えたことや迷ったことを個別に書いてきました。本記事では、それらの判断を「家庭内ポイント制度をどう要件定義し、どうLINE Botとして設計するか」という流れに整理し直しています。

#### 技術記事からの接続

技術記事から来た読者は、LINE Bot、Webhook、DB設計、UseCase設計などに関心を持っている可能性が高い。

そのため、無料部分では以下を伝える。

* 技術記事では、個別の設計・実装テーマを扱っている
* 有料記事では、それらをATS全体のユースケースとしてつなげる
* postback.data、Webhook、UseCase、DB更新、LINE返信の流れを順番に整理する
* 実装だけでなく、なぜその仕様・設計にしたのかを扱う

技術記事からの導線文は、以下のようにする。

> 技術記事では、Webhook、postback.data、DB設計、UseCase設計などを個別に扱ってきました。本記事では、それらをATSの中核ユースケースである「行動報告→ポイント付与→制限判定→DB更新→LINE返信」の流れとして再構成します。

#### 無料記事末尾からの導線

既存無料記事の末尾には、有料まとめ記事への導線を設置する。

導線文は、記事タイプごとに変える。

| 記事タイプ  | 導線文の方向性                                           |
| ------ | ------------------------------------------------- |
| 開発日記   | この判断を含めたATS全体の設計プロセスは有料まとめ記事で体系化している              |
| 技術記事   | この技術要素をATS全体の要件・DB・UseCase設計につなげた流れは有料まとめ記事で扱っている |
| 図解記事   | 図解で示した考え方を、実際の要件定義・実装へ落とす手順は有料まとめ記事で扱っている         |
| 振り返り記事 | 運用後の改善判断を含めた全体設計は有料まとめ記事で整理している                   |

導線文は、単なる販売告知ではなく、読者に次の理解を促すものにする。

> この記事では個別テーマとして扱いましたが、ATS全体の要件定義・設計・実装・運用改善の流れは、有料まとめ記事で体系化しています。

#### 有料記事側での既存記事の扱い

有料記事の無料部分では、既存記事へのリンクを配置する。

ただし、リンクを大量に並べるだけでは読者が迷うため、以下のように分類して提示する。

| 分類           | リンクする記事の方向性                                      |
| ------------ | ------------------------------------------------ |
| 背景を知りたい人向け   | 家庭内ポイント制度を作ろうとした話、紙運用から始めた話                      |
| 設計思想を知りたい人向け | ポイント・レベル・アイテムを分けた話、ポイントバランス調整の話                  |
| 技術面を知りたい人向け  | LINE Bot Webhook、postback.data、DB設計、UseCase設計の記事 |
| 運用改善を知りたい人向け | cooldown、daily_limit、冪等性、運用後の見直し記事               |

無料部分の最後または途中に、「先に読みたい人向けの無料記事」として案内する。

ただし、有料記事を読む前にすべての無料記事を読む必要はない。無料記事は補助導線であり、有料記事内では必要な背景を再整理する。

#### 既存無料記事との接続方針まとめ

既存無料記事との接続方針は、以下である。

1. 無料記事は、共感・信頼形成・導線として使う
2. 有料記事は、既存記事の単純な再録ではなく、実践順に再構成する
3. 開発日記から来た読者には、家庭内ルールを要件化する流れを示す
4. 技術記事から来た読者には、技術要素をユースケース全体に接続する流れを示す
5. 無料記事末尾には、有料まとめ記事への自然な導線を設置する
6. 有料記事の無料部分には、関連無料記事を分類して案内する
7. 無料記事を読んでいなくても、有料記事単体で理解できる構成にする

この方針により、無料記事群は単なる過去記事ではなく、有料まとめ記事への入口、信頼材料、補助教材として機能する。

## 9. 有料部分の構成方針

本章では、ATS有料まとめ記事における有料部分の構成方針を定義する。

有料部分は、無料部分で提示した問題提起に対して、具体的な設計手順、判断理由、実装への落とし込み、運用改善の考え方を提供する本体である。

本記事の有料部分は、既存記事の単純な再録ではなく、家庭内ポイント制度という現実の課題を、要件定義、仕様設計、LINE Bot設計、DB設計、実装、運用改善の順に再構成する実践ガイドとして設計する。

中心となる流れは以下である。

```text
家庭内の悩み
↓
要件定義
↓
行動・ポイント・制限の仕様化
↓
LINE Botの操作設計
↓
UseCase設計
↓
DB設計
↓
TypeScript実装
↓
手動確認
↓
運用改善
```

有料部分では、完成済みの正解を提示するのではなく、現実のあいまいな課題を、どのように仕様・設計・実装・運用へ変換したかを実例ベースで示す。

---

### 9.1 有料部分の基本構成

有料部分は、以下の4部構成とする。

| 部   | 位置づけ       | 役割                                     |
| --- | ---------- | -------------------------------------- |
| 第1部 | 要件定義編      | 家庭内の悩みを、システムで扱える要件へ変換する                |
| 第2部 | 仕様設計編      | 行動・ポイント・制限・ごほうびを仕様として定義する              |
| 第3部 | システム設計・実装編 | LINE Bot、UseCase、DB、TypeScript実装へ落とし込む |
| 第4部 | 運用改善・応用編   | 手動確認、運用後の見直し、読者自身の題材への応用を扱う            |

この4部構成により、読者は「なぜ作るのか」から「どう作るのか」までを順番に追える。

特に本記事では、第1部と第2部を厚めに扱う。理由は、家庭内ポイント制度の難しさは、コードを書く前の仕様化にあるためである。

有料部分の章構成は、以下とする。

| 章    | タイトル                    | 概要                                                                                |

| 第1章  | 家庭内の悩みを要件に変える           | 家庭内ポイント制度を作ろうとした背景を整理し、現実の悩みを機能要件・非機能要件に変換する。                                     |

### 9.3 章構成の意図

有料部分の章構成は、実装手順ではなく、設計の思考順に並べる。

本記事では、最初にLINE Botの作り方から入らない。まず、家庭内の悩みを要件として整理し、次に行動・ポイント・制限・ごほうびを仕様化する。そのうえで、LINE Bot、postback.data、UseCase、DB、TypeScript実装へ落とし込む。

この順番にする理由は、ATSの価値が「LINE Botを作ったこと」ではなく、「現実の家庭内ルールを、壊れにくい仕組みに変換したこと」にあるためである。

そのため、有料部分では以下の順番を重視する。

1. 家庭内課題を整理する
2. 紙運用から仕様の種を集める
3. 行動・ポイント・制限・ごほうびを仕様化する
4. LINE Botの操作に落とす
5. UseCaseとして業務処理を固定する
6. DB設計で正本を作る
7. TypeScript実装へ落とす
8. 手動確認する
9. 運用しながら改善する
10. 読者自身の題材へ応用する

この順番により、読者は単なるコード例ではなく、現実の課題をシステムへ変換する流れを学べる。

## 10. 特典・副産物設計

本章では、ATS有料まとめ記事に付属させる特典・副産物の設計方針を定義する。

本記事の特典は、単なるおまけではなく、本文で解説する要件定義・仕様設計・LINE Bot設計・DB設計・運用改善を、読者が自分の題材に転用するための補助教材として位置づける。

特典の目的は、以下である。

* 読者が本文を読んだだけで終わらず、自分の題材に応用できるようにする
* 家庭内ポイント制度や個人開発の設計を、具体的なシートやテンプレートに落とし込めるようにする
* 有料記事としての実用価値を高める
* 既存の技術記事・開発日記で扱ってきた設計知見を再利用しやすくする
* 将来の追記・更新によって、有料記事を資産化しやすくする

ただし、初版から特典を増やしすぎない。

特典が多すぎると、記事の公開が遅れ、読者にとっても何から使えばよいか分かりにくくなる。そのため、初版では、ATSの中核スコープである「行動報告・ポイント付与・制限判定・DB設計・LINE Bot基本設計」に直結するものを優先する。

---

### 10.1 特典・副産物の基本方針

特典・副産物は、以下の方針で設計する。

| 方針            | 内容                                         |
| ------------- | ------------------------------------------ |
| 本文と対応させる      | 特典だけを独立させず、本文の各章と対応させる                     |
| 初版は中核機能に絞る    | 行動報告、ポイント設計、制限設計、LINE Bot、DB設計に直結するものを優先する |
| コピペ完成品にしない    | 完成アプリではなく、読者が自分の題材に合わせて使える設計補助にする          |
| 使い方を本文で説明する   | テンプレートを渡すだけでなく、どの章でどう使うかを本文内で説明する          |
| 更新可能な形にする     | 将来追記しやすいよう、初版特典と追加予定特典を分ける                 |
| 家庭情報に依存させすぎない | ATSの実例を使いつつ、読者が自分の家庭・個人開発・業務改善に応用できる形にする   |

本記事の特典は、「これを使えば完成品が手に入る」というものではない。

むしろ、本文で扱う判断過程を読者が再利用できるようにするための設計道具である。

### 10.3 初版特典の詳細

#### 10.3.1 行動マスタ設計テンプレート

行動マスタ設計テンプレートは、家庭内ポイント制度や個人開発における「報告対象の行動」を整理するためのテンプレートである。

想定項目は、以下である。

| 項目               | 内容            |
| ---------------- | ------------- |
| category_code    | 行動カテゴリのコード    |
| category_name    | 行動カテゴリ名       |
| action_code      | 行動を識別するコード    |
| action_name      | LINE上に表示する行動名 |
| point_value      | 付与ポイント        |
| daily_limit      | 1日の上限回数       |
| cooldown_seconds | 連打防止時間        |
| note             | 設計メモ、判断理由     |

この特典では、ATSで実際に使用した考え方をベースにしつつ、読者が自分の家庭や題材に合わせて調整できる形にする。

目的は、行動を「なんとなくのリスト」ではなく、システムで扱えるマスタデータとして整理できるようにすることである。

---

#### 10.3.2 ポイントバランス調整シート

ポイントバランス調整シートは、行動ポイント、日次上限、ごほうび価格のバランスを検討するためのシートである。

想定項目は、以下である。

| 項目               | 内容            |
| ---------------- | ------------- |
| action_name      | 行動名           |
| point_value      | 1回あたりの付与ポイント  |
| daily_limit      | 1日の上限回数       |
| max_daily_point  | 1日最大獲得ポイント    |
| weekly_estimate  | 週あたりの想定獲得ポイント |
| monthly_estimate | 月あたりの想定獲得ポイント |
| reward_name      | ごほうび名         |
| required_points  | 必要ポイント        |
| estimated_days   | 到達までの想定日数     |
| note             | 調整メモ          |

この特典では、ポイント制度がインフレしないように、行動ポイントと報酬価格をセットで見られるようにする。

目的は、ポイント値を感覚だけで決めず、日次・週次・月次の獲得量から逆算して設計できるようにすることである。

---

#### 10.3.3 postback.data設計テンプレート

postback.data設計テンプレートは、LINE Botのボタン操作をサーバー側の処理に接続するための操作契約を整理するテンプレートである。

想定項目は、以下である。

| 項目             | 内容                        |
| -------------- | ------------------------- |
| type           | 操作種別                      |
| 表示名            | LINE上でユーザーに見えるラベル         |
| postback.data例 | 実際に送信するデータ例               |
| 必須パラメータ        | actionCode、categoryCodeなど |
| 遷移先 / 呼び出し先    | 対応するUseCaseや処理            |
| 成功時レスポンス       | 正常時の返信方針                  |
| 異常時レスポンス       | 制限違反・不正値などの返信方針           |
| note           | 設計メモ                      |

この特典では、postback.dataを単なる文字列ではなく、UIとUseCaseをつなぐ契約として扱う。

目的は、LINE Botの実装が場当たり的にならないよう、操作種別とパラメータを事前に固定できるようにすることである。

---

#### 10.3.4 DB設計テンプレート

DB設計テンプレートは、ATSのような行動記録・ポイント付与システムに必要なテーブル責務を整理するためのテンプレートである。

想定項目は、以下である。

| 項目                 | 内容               |
| ------------------ | ---------------- |
| table_name         | テーブル名            |
| responsibility     | そのテーブルの責務        |
| main_columns       | 主要カラム            |
| primary_key        | 主キー              |
| unique_constraints | UNIQUE制約         |
| indexes            | 想定インデックス         |
| updated_by_usecase | どのUseCaseで更新されるか |
| transaction_scope  | トランザクションに含めるか    |
| note               | 設計メモ             |

この特典では、users、actions、activity_logs、daily_point_summaries、processed_eventsなどの責務分担を整理する。

目的は、DBを単なる保存先ではなく、業務判定と履歴の根拠となる正本として設計できるようにすることである。

---

#### 10.3.5 手動テストチェックリスト

手動テストチェックリストは、実装後に仕様通り動いているかを確認するためのチェックリストである。

想定項目は、以下である。

| 確認分類              | 確認内容                                                       |
| ----------------- | ---------------------------------------------------------- |
| 正常系               | 行動報告後、ポイントが付与される                                           |
| DB更新              | activity_logs、daily_point_summaries、processed_eventsが更新される |
| cooldown          | 連続実行時に制限される                                                |
| daily_limit       | 同一行動の上限を超えると拒否される                                          |
| daily_point_limit | 日次上限を超えると拒否される                                             |
| 冪等性               | 同一イベントが二重計上されない                                            |
| LINE返信            | 成功時・制限違反時の文言が意図通り返る                                        |
| 異常系               | 不正なpostback.dataを受けても壊れない                                  |
| 運用確認              | 親がDBやログから状態を確認できる                                          |

この特典では、テストコードを書く前段階として、手動で仕様を確認する観点を整理する。

目的は、個人開発において「動いた気がする」で終わらせず、最低限の確認観点を持てるようにすることである。

### 10.6 初版では提供しないもの

以下は、初版では提供しない。

| 提供しないもの           | 理由                               |
| ----------------- | -------------------------------- |
| 完成済みLINE Botアプリ一式 | 家庭ごとの調整が必要であり、保守負担も大きいため         |

| 育児ノウハウ集           | 本記事の中心価値は育児論ではなく、要件定義・設計・実装にあるため |
| 万能ポイント制度テンプレート    | 家庭ごとに行動、報酬、制限が異なるため              |
| 完全なDDD教材          | 必要な責務分担は扱うが、理論の網羅は目的ではないため       |

| 個別相談・個別カスタマイズ     | 有料記事単体の商品として扱うため                 |

これらを明確にしておくことで、読者の期待値を調整し、購入後のミスマッチを防ぐ。

### 10.7 特典の提供形式

特典の提供形式は、以下を基本とする。

| 形式            | 用途                       |
| ------------- | ------------------------ |
| Markdown      | 設計テンプレート、チェックリスト、仕様整理    |
| Google Sheets | ポイントバランス調整、行動マスタ整理       |
| Mermaid       | フロー図、DB関係図、UseCaseフロー    |
| コードスニペット      | 設計意図を説明するための最小限の実装例      |
| GitHub        | 将来、サンプルコードを整理する場合の候補     |
| Notion        | 将来、閲覧・運用テンプレートを提供する場合の候補 |

初版では、MarkdownとGoogle Sheetsを中心にする。

理由は、読者が扱いやすく、記事本文との相性もよく、作成・更新の負担が比較的低いためである。

GitHubサンプルコードやNotionテンプレートは、初版公開後の反応を見て追加する。

### 10.8 特典と価格方針の関係

特典は、価格方針にも影響する。

初版で提供する特典が本文補助レベルに留まる場合、価格は中価格帯から始めるのが現実的である。

一方で、Google Sheetsテンプレート、設計テンプレート、チェックリスト、サンプルコード、Notionテンプレートなどが充実してくると、記事単体ではなく「設計キット」としての価値が高まる。

そのため、価格は以下のように段階設計する余地がある。

| 段階  | 特典状態                            | 価格イメージ    |
| --- | ------------------------------- | --------- |
| 初版  | 本文＋主要テンプレート5点                   | 中価格帯      |
| 改訂版 | テンプレート追加、図解追加、運用改善追記            | 中〜やや高価格帯  |
| 拡張版 | GitHubサンプル、Notion/Sheets、将来機能追記 | 高価格帯も検討可能 |

ただし、価格そのものは第11章「価格方針」で検討する。

本章では、価格を直接決めるのではなく、価格を支える特典価値を整理する。

---

### 10.9 特典・副産物設計のまとめ

特典・副産物設計の方針は、以下である。

1. 特典は本文の補助教材として設計する
2. 初版では、ATSの中核機能に直結する5つの特典に絞る
3. コピペ完成品ではなく、読者が自分の題材に応用できる設計テンプレートにする
4. MarkdownとGoogle Sheetsを中心に提供する
5. GitHubサンプルコードやNotionテンプレートは、初版では必須にしない
6. 将来追記として、スタンプ、抽選、ボーナス、取り消し、登録支援に対応する特典を追加する
7. 初版で提供しないものを明確にし、購入後のミスマッチを防ぐ
8. 特典の充実度に応じて、将来的な価格改定の余地を残す

この方針により、有料まとめ記事は単なる長文記事ではなく、読者が自分の家庭・個人開発・業務改善に応用できる実践キットとして成立する。
